# 概念解释写作契约

适用于读者对 MCP、Skill、Agent、Workflow、模型能力、提示词等概念有具体困惑的文章。目标不是做一张完整知识图谱，而是帮读者改掉一个会影响行动的误解。

## 动笔前

从已给材料中写下四件事：

1. **现场**：一条笔记、一次操作、一个错误判断或一段真实对话；不能凭空补。
2. **卡点**：这个现场让读者或作者原来以为的什么东西失效了。
3. **机制**：用一个人话解释说明为什么会这样，并说明适用边界。
4. **变化**：读完后，读者下一次会怎样提问、选择或操作。

现场必须参与论证。它不能只在开头出现一次，后文换成任何案例都不受影响。

如果材料只够解释定义，不足以支持现场和变化，输出带来源的研究提纲或明确说明缺什么；不要伪装成第一人称复盘。

## 结构预算

推荐顺序：现场或困惑 → 拆开一个误解 → 机制与边界 → 一个会改变判断的例子 → 下一步。

每一节只承担一个任务。全文只选一个主要的判断工具：类比、对比表、决策路径或问题清单之一。后面的工具如果仍在回答同一个问题，就合并或删除，不用“完整感”填充结构。

表格适合比较对象；问题清单适合帮助读者行动；两者同时出现，必须分别回答不同问题。段落里已经完成的判断，不再用另一组同义标题重复一次。

## 结尾门槛

结尾要带来增量：给出一个下一步动作、留下一个仍待验证的边界，或回到开头现场说明工作方式怎样变了。

不要把开头的中心判断换一组同义词再说一遍，也不要用“所以 Prompt、Skill、流程都很重要”这类可放进任何文章的总结卡片收尾。

## 交付前自查

- 删掉开头现场后，中心判断是否失去依据？若没有，现场只是装饰。
- 相邻段落是否各自新增机制、例子、边界或决定？
- 是否叠加了两套回答同一个问题的表格、清单或框架？
- 收尾是否改变读者的下一步，而不是复述全文？
